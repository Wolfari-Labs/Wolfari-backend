# Finance notification inbox

Automation consumes `ContributionRequested` for currently eligible debtors, `ClosureRequested` for required closure members still unconfirmed, and `ContributionUpdated` to notify the current Holder of a report awaiting review. They create generic `AVAILABLE` in-app notifications exposed by the existing Self inbox API126–131. Closure messages include a per-recipient rolling 24-hour limit. This slice does not send push/email, run an automatic reminder scheduler, cancel previously available notices, or handle ClosureCancelled/FinanceClosed.

## Source and scope

The business baseline is [SRS 2.3](../Wolfari_SRS_v2.3_ChinhThuc.docx), FR-FN02/FR-FN08/FR-AU01 and sections 9.1/9.4/9.5, with event payloads in [DDL/API/Event 1.1](../Wolfari_DDL_API_Event_Specification_v1.1_ChinhThuc.docx). Queue names, the consumer name, generic content and rolling-window rule below are implementation conventions for review, not new assertions of source-document approval. Retention and production acceptance remain open.

The request writer inserts all contributions and their IDs in one Finance transaction. No existing API adds or reassigns debtors within an existing request; new obligations need a new request. Consequently the current request audience is a subset of the original event audience. A later join adds no obligation, and Finance excludes a rejoined membership newer than its old contribution. Revisit this invariant before adding any recipient-editing API. The actor is included when they are also an eligible debtor.

Closure creation (API120) captures required members in an immutable snapshot. Explicit reminders (API125) emit another `ClosureRequested` with a new event ID, potentially at the same Fund version. Both use current Finance context purpose `CLOSURE`, so only still-unconfirmed, eligible members are considered while Fund is CLOSING and closure is PENDING_CONFIRMATIONS. Owner/Self is included when unconfirmed; confirmed, cancelled/completed, archived or departed sources cannot create new notices. Inactive accounts are excluded. The event's `snapshot_hash` is validated and fingerprinted; the existing context response has no hash field, so this consumer does not claim to compare it with a separately returned current snapshot hash. A cancelled closure and its replacement have different source IDs and independent limits.

## Processing and privacy

1. Validate the compatible v1 envelope, Finance producer, event type, UUIDs, unique contribution IDs or closure snapshot hash, and envelope/payload consistency. Project known fields only. Additive fields never become message content.
2. Check Automation's durable inbox for this event ID. An identical processed event needs no external read; reuse of that ID with a different known-field fingerprint goes to DLQ.
3. Call [Finance.GetAutomationContext](finance-automation-context.md) with `CONTRIBUTION_REQUEST` and the request ID, `CLOSURE` and the closure ID, or `CONTRIBUTION_REVIEW` and the contribution ID. Accept a current Fund version at least as new as the event. Review also requires a positive `source_revision`; review/closure context must not contain a deadline. No Fund-version deduplication is used.
4. Check [Identity.GetNotificationEligibility](notification-account-eligibility.md) in batches of at most 100. Missing/inactive accounts are excluded. Each response must account for the whole batch; a dependency failure or malformed response retries the entire event.
5. Re-read Finance and compare version, status, recipients, deadline and review source revision. A changed source retries. Two matching trusted missing-source results, or a stable ineligible/empty source, commit a suppressed inbox result.
6. Atomically claim `inbox_events(consumer_name,event_id)`, apply the closure cooldown or review-revision deduplication where applicable, and create accepted notifications in `automation_db`, then ACK. Request/closure dedupe keys retain event ID and user ID; review uses contribution ID, current source revision and Holder ID. SQL failure rolls back both; a lost ACK may redeliver but cannot create a second set of rows. Original ContributionRequested/ClosureRequested fingerprints and the durable consumer name `AutomationFinanceContributionInbox` are retained across this extension.

Finance checks current Trip state and membership. Identity and Finance reads are observations, not a distributed transaction: source/account state can change after a successful check. Every RPC has at most two seconds and the orchestration shares ten seconds. SQL work has a five-second response budget after bounded pool acquisition; a failed/uncertain connection is destroyed. There are no network calls in the SQL transaction and no cross-database SQL.

Contribution notices use type `CONTRIBUTION_REQUESTED` and title `Yêu cầu đóng góp`; closure notices use `CLOSURE_REQUESTED` and `Yêu cầu xác nhận đóng quỹ`; Holder review uses `CONTRIBUTION_REVIEW` and `Báo chuyển chờ xác nhận`. All carry identifiers and generic text asking the recipient to open the Trip for current information. No amount, account number, request title/note, closure snapshot, email or receipt data is copied. No delivery row is created. Push/email preferences do not disable in-app notifications. Existing notices remain history; [Self inbox authorization masking](notification-management.md) still applies on reads. Runtime warnings contain fixed error codes, not payloads, credentials or SQL errors.

## Holder report review

ContributionUpdated is an invalidation signal for current state. API081 request title/note changes emit it even when the contribution remains TRANSFER_REPORTED, without increasing contribution.version. Therefore a new event ID does not necessarily mean a new report. Finance context returns the existing contribution.version as optional `source_revision` for CONTRIBUTION_REVIEW only. Missing/invalid revision retries; the worker does not guess from Fund version or treat an older Finance response as successful suppression.

Fund and request must be OPEN, contribution TRANSFER_REPORTED, Trip active, and the current Holder authorized with an active account. At most one recipient is accepted, including a Holder reporting their own contribution. A delayed event with an older status can discover a newer valid report; it only creates the current revision's notice. Current confirmation/waiver/cancellation/reversal or closure suppresses the notice. Two matching source reads remain observations, not a cross-service lock.

The existing unique notification key `finance-review:<contribution_id>:<source_revision>:<holder_id>` serializes competing inserts. Distinct event inbox claims commit even when their notice is suppressed by that key. Metadata changes produce no repeated review notice; rejection and a later report increase contribution.version and allow a new one. Inbox results include source revision and duplicate-suppressed count. A failed/timed-out insert rolls back its inbox claim, including waits on a concurrent unique-key conflict. No new schema or financial writer is added, and existing notifications remain history. Review handling does not implement ContributionUpdated's future reminder rescheduling/cancellation responsibilities.

## Closure reminder limit

The first AVAILABLE closure notice starts a rolling 24-hour window for that closure/user. A distinct event within the window is processed durably but does not create another notice for that recipient. It is not scheduled for later. An explicit new reminder after at least 24 hours may notify that user if source/account checks still pass. Replaying a processed event, including a fully suppressed reminder, never creates a later notification. Mixed audiences are evaluated individually, and a new closure ID has a new window.

The repository starts an explicit READ COMMITTED transaction, claims the event, and acquires transaction-scoped advisory locks for normalized/sorted closure-user keys. After all locks are held, it checks existing notification history and inserts eligible rows in one statement. `statement_timestamp()` gives that statement a consistent cutoff and creation time after lock waits; `interval '24 hours'` avoids calendar-day/DST ambiguity. The latest qualifying notice at exactly 24 hours is outside the suppressed interval. Inbox results record created and cooldown-suppressed counts; all writes commit together. No RPC occurs under these locks, and timeout/failure destroys the connection and rolls back the inbox claim and locks.

This uses the existing notification history without adding a schema or retention policy. The cooldown lookup includes historical statuses so later cancellation does not erase a recent send from the window. Purging recent history would invalidate the limit and requires a separate retention design; no purge exists here. Very large audiences/history still share the existing bounded SQL budget and may retry; this is not a load-capacity claim.

The lock/isolation and timestamp choices follow PostgreSQL 17 [advisory-lock semantics](https://www.postgresql.org/docs/17/explicit-locking.html#ADVISORY-LOCKS), [READ COMMITTED snapshots](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED) and [statement timestamps](https://www.postgresql.org/docs/17/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT).

## Broker ownership and recovery

The dedicated `wolfari.automation.finance-notifications.v1` queue binds `ContributionRequested`, `ClosureRequested` and `ContributionUpdated` on `wolfari.events.v1`. Their catalog bindings move out of the general Automation queue; the worker never consumes that general queue. The catalog does not provision or remove previously deployed bindings. Deploy Finance with review source_revision first and drain/replace older consumers before activating the new binding: older workers reject event types they do not support. This change does not implement mixed-version rolling deployment.

The main queue, `.dlq` and `.retry.0` through `.retry.4` are durable quorum queues. Retry TTLs are 10, 30, 120, 300 and 900 seconds. Retry queues use at-least-once dead lettering with `reject-publish`, routing back to the main queue through the default exchange. Delivery limits are disabled so quorum redelivery does not silently discard a message after repeated lost acknowledgements. A single-node test proves persistence/restart behavior, not replicated high availability.

The header `x-finance-notification-attempt` counts five explicit retries. Invalid contracts/identity collisions go directly to DLQ; dependency/SQL failures go there after exhaustion. Retry/DLQ publication preserves the original body/event ID, uses persistence, mandatory routing and publisher confirms, and ACKs the original only after positive confirmation without a return. An uncertain transfer closes the session and leaves the original unacknowledged. This may duplicate a transfer; the durable inbox prevents repeated notification effects. A unique transfer token correlates concurrent mandatory returns even for the same message ID.

Setup, confirmation, socket handshake and RPC/SQL waits are bounded. Shutdown aborts the broker socket and drains bounded processing. Interrupted work can commit before disconnect is observed; redelivery then resolves through the inbox. There is no purge, automatic poison replay, or promise of global event order.

For operator recovery, inspect the retained DLQ entry and its generic reason, fix the dependency/contract issue, then republish the **unchanged body and event ID**, resetting the retry header. Require confirmed routing before removing the retained entry. No general-purpose replay CLI or shared-environment replay is included in this slice; the isolated fixture verifies same-ID replay. Changing the event identity would bypass the intended deduplication.

## Configuration and acceptance

`AUTOMATION_FINANCE_NOTIFICATION_ENABLED=false` is the default; only literal `true` enables the consumer. Enabled mode needs the existing RabbitMQ URL, Finance/Identity loopback gRPC targets and Automation's own service credentials. Production startup remains blocked until TLS is implemented. No new credential, schema migration, REST endpoint, protobuf method or event payload is added.

Keep shared `FINANCE_OUTBOX_ENABLED` disabled until **all intended Finance event bindings and consumers** are accepted. These bindings do not complete ContributionUpdated reminder scheduling, ClosureCancelled or FinanceClosed. Existing general bindings, if manually provisioned elsewhere, need an explicit deployment review. No development environment is activated by this change.

Run `corepack pnpm finance:notification:test` for isolated PostgreSQL/RabbitMQ/MinIO plus Identity, Trip, Finance, Automation and Gateway. It covers real API078 → outbox → broker → Self inbox, current source/account suppression, membership changes, more than 100 recipients, preferences off, SQL rollback/concurrency, duplicates, crash after commit before ACK, dependency retry, DLQ/replay and broker restart. Unit tests cover malformed responses, source changes, exact retry/confirm behavior, bounded shutdown and real stalled TCP cancellation. CI has a separate job; local results do not establish remote CI or production acceptance.

The closure fixture adds real API120/API125, unchanged-version reminder IDs, per-user cooldown boundaries, concurrent reminders, confirmed/cancelled/completed sources, replacement closures, account/rejoin checks, 103 recipients, failed insert and held-lock timeout, dependency retry, DLQ/replay, actual consumer process death and broker restart. It uses synthetic data and controlled fixture timestamps; no real reminders or provider messages are sent.

The Holder fixture adds real report/reject/confirm and metadata APIs, Self inbox, report revision over gRPC, concurrent same-revision events, stale event status, current account/membership/lifecycle suppression, transactional failures/unique-key timeout, dependency outages, DLQ replay, process death after commit before ACK and broker restart. Synthetic SQL fixtures isolate failure/concurrency behavior; they do not establish real bank/provider acceptance.
